# Apartment Lease Details + Google Sheet / Rentvine Push (Phase 2) — Design

**Date:** 2026-07-27
**Status:** Approved
**Depends on:** Phase 1 (`docs/superpowers/specs/2026-07-27-lease-renewals-supabase-design.md`) — the existing `lease_renewals` table and Rentvine tab's "Sync Now" flow are unchanged and untouched by this phase, except that the same sync endpoint gains an additional automatic trigger.

## Background

Phase 1 built a persisted, color-coded Lease Renewals table (formal renewals + expiring leases) synced from Rentvine on manual button press. The team also maintains a separate Google Sheet ("List of Renewals Leases") by hand, tracking every apartment/unit with columns Rentvine doesn't have (Security Deposit, Notes, Lease Status override, Lease Sent status/date, a document Link) alongside some Rentvine has (tenant, lease dates, rent).

Phase 2 goal: give the dashboard a second, editable table covering **all** apartments (not just ones with a formal/expiring renewal), matching the sheet's columns, with the ability to push edits to Supabase, the Google Sheet, and (for the renewal-date fields only, for now) Rentvine itself — independently, via three separate per-row buttons.

## Rentvine API findings (read-only investigation, 2026-07-27)

- No standalone unit/vacancy-list endpoint (`/units` → 404). The closest to "all apartments" is `GET /leases` **unfiltered** (no `leaseStatusID`), which returns every lease record regardless of status, each with a nested `unit` object.
- Pagination is real: `per-page` appears capped at 25 regardless of the requested value; multiple pages exist beyond that (confirmed via `page=2` returning different `leaseID`s). A full fetch must loop pages until an empty page is returned.
- The nested `unit` object already has **native** `deposit` and `leaseNotes` fields — Security Deposit and Notes aren't purely invented sheet columns.
- `GET /leases/renewals`'s `renewal` object has `previousStartDate`/`previousEndDate` (→ Activation 1/Expiration 1) and `startDate`/`endDate` (→ Activation 2/Expiration 2, the renewal term) — this is the source for the sheet's two date-pair columns, but **only for leases that have a formal renewal record**. Leases without one only get Activation 1/Expiration 1 from `lease.startDate`/`lease.endDate`.
- No field anywhere in Rentvine corresponds to "New Rent" — confirmed manual-only.
- A currently-vacant unit with zero lease history ever created **will not appear** via `/leases` at all — Rentvine exposes no way to enumerate such units through this API. Rows like that in the sheet stay manual-only entries in `apartment_lease_details` (source: not tied to a Rentvine lease).
- **Write endpoint for the renewal date fields is unverified.** Best-guess shape based on Rentvine's REST conventions: `PATCH /api/manager/leases/renewals/{leaseRenewalID}` with `{ startDate, endDate }`. Per explicit user instruction, no test write was performed — this will be confirmed/corrected against the real API the first time "Save to Rentvine" is actually clicked, debugging live against whatever response comes back.

## Architecture

```
Existing (Phase 1, unchanged):
"Sync Now" button → POST /api/rentvine/lease-sync → upserts lease_renewals
+ NEW: n8n Schedule Trigger (cron 0 15 * * *, daily 3pm) also POSTs to /api/rentvine/lease-sync
  (n8n-side workflow, no application code change — this endpoint already exists and is idempotent via upsert)

NEW (Phase 2):
"Fetch All Apartments" button (rendered below the existing Lease Renewals table, same tab)
  → POST /api/rentvine/apartment-details-sync
      → paginate GET /leases (all statuses, all pages) + GET /leases/renewals
      → upsert into public.apartment_lease_details, keyed on (address, unit)
  → GET /api/rentvine/apartment-details
      → reads apartment_lease_details from Supabase (persists across page refresh)
  → New editable table renders it, columns matching the Google Sheet

Per-row actions (3 independent small buttons, far right of each row):
  "Save to Supabase" → PATCH /api/rentvine/apartment-details/:id → writes edited row to Supabase
  "Save to Sheet"     → POST /api/rentvine/apartment-details/:id/push-sheet → writes matching row in Google Sheet
  "Save to Rentvine"  → POST /api/rentvine/apartment-details/:id/push-rentvine → PATCHes Rentvine's renewal endDate/startDate
```

Row highlighting: any row in the new table whose address+tenant matches a row currently displayed in the top Lease Renewals table is visually flagged, so units needing renewal attention stand out in the full list.

## Data model

```sql
create table public.apartment_lease_details (
  id bigint generated by default as identity primary key,
  address text not null,
  unit text not null default '',            -- "Room Floor" (e.g. "2R"), blank for single-unit properties
  tenant_name text,
  activation_1 date,                         -- current lease start (Rentvine: lease.startDate, or renewal.previousStartDate if a renewal exists)
  expiration_1 date,                         -- current lease end (Rentvine: lease.endDate, or renewal.previousEndDate)
  activation_2 date,                         -- renewal term start (Rentvine: renewal.startDate) — EDITABLE this phase
  expiration_2 date,                         -- renewal term end (Rentvine: renewal.endDate) — EDITABLE this phase
  new_rent numeric(12,2),                    -- manual only, no Rentvine source
  current_rent numeric(12,2),                -- Rentvine: unit.rent
  security_deposit numeric(12,2),            -- Rentvine: unit.deposit
  lease_status text,                         -- manual dropdown, no Rentvine equivalent
  notes text,                                -- Rentvine: unit.leaseNotes
  lease_sent text,                           -- manual dropdown, no Rentvine equivalent
  lease_sent_date date,                      -- manual
  link text,                                 -- manual
  rentvine_lease_id text,                    -- nullable — set when a Rentvine lease exists for this row
  rentvine_unit_id text,                     -- nullable
  rentvine_lease_renewal_id text,            -- nullable — needed to construct the Rentvine PATCH URL; null if no formal renewal exists yet
  source text not null default 'manual',     -- 'rentvine' | 'manual'
  updated_at timestamptz not null default now(),
  unique (address, unit)
);

create index apartment_lease_details_address_idx on public.apartment_lease_details (address);

alter table public.apartment_lease_details enable row level security;
revoke all on public.apartment_lease_details from anon, authenticated;
grant all on public.apartment_lease_details to service_role;
```

- RLS: same locked pattern as `lease_renewals` (service-role only, browser never touches it directly).
- **Sync conflict rule:** re-running "Fetch All Apartments" always overwrites Rentvine-sourced fields (`tenant_name`, `activation_1/expiration_1`, `current_rent`, `security_deposit`, `notes`) with whatever Rentvine currently has, even if a human edited them since — confirmed acceptable by the user for this phase. Manual-only fields (`new_rent`, `lease_status`, `lease_sent`, `lease_sent_date`, `link`) are never touched by the Rentvine sync. `activation_2`/`expiration_2` (the fields this phase actually edits) are also overwritten by sync from `renewal.startDate`/`renewal.endDate` when a formal renewal exists in Rentvine — a human edit to these via "Save to Rentvine" is expected to already be reflected back in Rentvine by the time of the next sync, so this isn't a real conflict in practice.

## UI

- New section below the existing Lease Renewals table on the Rentvine tab: "Fetch All Apartments" button + table.
- Columns: Address, Unit, Tenant, Activation 1/Expiration 1, Activation 2/Expiration 2, New Rent, Current Rent, Security Deposit, Lease Status, Notes, Lease Sent, Date, Link — matching the sheet's layout.
- Row highlighting: cross-reference against the currently-loaded top table's rows (by address+tenant) to flag units needing renewal attention.
- **This phase only makes Activation 2 / Expiration 2 editable inline** (date inputs). All other columns render read-only for now; more fields become editable in later iterations per user direction.
- Far right of each row: 3 small independent buttons — "Save to Supabase", "Save to Sheet", "Save to Rentvine". Each is its own request; a failure in one does not block or roll back the others.
- Persisted across refresh: the table always reads from `GET /api/rentvine/apartment-details` (Supabase), same pattern as Phase 1's Lease Renewals table — a page reload does not lose data, though (same caveat as Phase 1) a `localStorage` cache may show stale data until either button is pressed again.

## Google Sheets integration (revised — n8n-mediated, not direct API)

The n8n "Google Sheets account" credential turned out to be an OAuth user-login connection (`rentshield10@gmail.com`), not a portable service account key — not something that can be copied into Next.js server env vars. Rather than standing up a separate service account, the write path goes through n8n instead, reusing its existing authorized connection:

```
"Save to Sheet" button (RentvineTab, new apartment details table)
  → POST /api/rentvine/apartment-details/:id/push-sheet (Next.js, our server)
      → POST to an n8n Webhook URL, body: { address, unit, activation2, expiration2 }
          → n8n workflow: Webhook → read all sheet rows → find row matching Address+Room Floor (Code node) → write F/G cells by explicit range (HTTP Request node, raw Sheets API values.update) → Respond to Webhook
      → our route relays n8n's response back to the browser
```

- **Row matching:** the sheet has repeated `Address` values across multiple units (e.g. "1208 43rd St" appears once per room) and no unique ID column, and its second Activation/Expiration column pair (F/G) shares the exact same header text as the first pair (D/E) — both problems ruled out matching/mapping by column name. No sheet changes are made (confirmed: skip adding any helper column, skip renaming headers). Instead, the n8n workflow reads all rows, filters for the one matching `Address` + `Room Floor` in a Code node to get its `row_number`, then writes directly to that row's F/G cells via a raw Google Sheets API `values.update` call on an explicit range (`Sheet1!F{row}:G{row}`) — bypassing column-name mapping entirely. See `docs/superpowers/n8n-mission-control-update-renewal-dates.json` (workflow to import) and its companion `...-SETUP.md`.
- **Write scope:** only Activation 2 / Expiration 2 (sheet columns F/G) are written, leaving Notes/Lease Sent/etc. untouched.
- **n8n webhook URL:** stored as a server-only env var `N8N_APARTMENT_SHEET_WEBHOOK_URL` in `.env.local` (already set), same trust boundary as other server secrets — never exposed to the browser.
- If no row matches Address+Room Floor in the sheet, the n8n workflow's Code node throws, which surfaces back through our route as a clear "Save to Sheet" failure (not a silent no-op, and not an auto-append — appending was the original intent but the final n8n workflow errors instead, which is simpler and safer for existing rows).
- The n8n workflow (`docs/superpowers/n8n-mission-control-update-renewal-dates.json`) has already been imported into n8n, credentials fixed, and is ready to receive webhook calls at the URL now stored in `.env.local`. Not yet end-to-end tested with a real write.

## Rentvine write (renewal dates only)

- `PATCH /api/manager/leases/renewals/{leaseRenewalID}` with `{ startDate, endDate }` — unverified shape, to be corrected live against the real API response on first use, per explicit user instruction to skip a pre-emptive test write.
- Only applies to rows that already have a `rentvine_lease_renewal_id` (i.e. a formal renewal exists in Rentvine). For rows without one, "Save to Rentvine" should return a clear "no renewal record exists in Rentvine for this lease yet" error rather than attempting an invalid write.
- No write attempted for any other field in this phase (Security Deposit, Notes, etc. stay Supabase+Sheet only until the user explicitly extends this).

## n8n cron (Phase 1 sync, now automated)

- User will add an n8n workflow: Schedule Trigger, cron `0 15 * * *` (3pm daily, local time) → HTTP Request node → `POST /api/rentvine/lease-sync`. No application code changes needed — this endpoint already exists (Phase 1) and is idempotent via upsert-on-`lease_id`. The existing manual "Sync Now" button is unaffected and stays available for on-demand refresh.

## Error handling

- All new routes use the same structured error shape as Phase 1 (`{ok:false, error, detail:{code,details,hint}}`).
- The three per-row save buttons are fully independent requests — a Rentvine write failure does not prevent or roll back a successful Supabase or Sheet write, and vice versa.

## Testing / verification

Same approach as Phase 1 — no automated test framework in this repo. Verification via `npx tsc --noEmit`, `npm run lint`, curl/REST checks for the sync and Supabase-write paths, and manual review (with the user, live) for the Sheet write and Rentvine write paths, since those touch real external systems that can't be safely dry-run without live credentials/data in hand.

## Out of scope (this phase)

- Editing any column besides Activation 2 / Expiration 2 (more fields to be opened up later per user direction).
- Writing Security Deposit/Notes/etc. back to Rentvine.
- Automatic Sheet→Supabase pull (this phase is Supabase/Rentvine→Sheet push only, via explicit button).
- Handling genuinely vacant units with zero Rentvine lease history (they simply won't populate from "Fetch All Apartments"; anyone can still add such a row manually if the UI later supports manual row creation — not building manual row creation in this phase).
