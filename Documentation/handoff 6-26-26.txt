# Mission Control Messages Automation — Current Handoff

**Date:** 2026-06-26  
**Project:** Mission Control Dashboard + Quo/OpenPhone + QuoSender + Web Auto Sender  
**Current focus:** Keep the automation rule intentionally strict, improve preview visibility, and prepare for webhook-based inbound message detection later.

---

## 1. Current Goal

Mission Control should become the control center for messaging automation.

The current flow is:

```text
n8n sends intro SMS
→ lead replies in Quo/OpenPhone
→ Mission Control checks messages
→ automation applies a conservative rule
→ if safe, render requirements template preview
→ if not safe, send to Human Review
→ later, Web Auto / auto-clicker sends SMS
→ Supabase lead pipeline updates only after successful send
```

The immediate goal is **not full auto-send yet**. The current goal is:

```text
Detect clean intro + one lead reply
→ match the correct lead/apartment
→ pull/render the QuoSender requirements template
→ show a preview pane with the rendered SMS
→ verify variables like apt address, price, schedule, and other template values
```

---

## 2. Important Agreement From Latest Discussion

We agreed to keep the current strict automation rule for testing.

### Do not loosen the rule yet

The rule should remain:

```text
Only auto-select requirements template when the whole conversation has exactly:
1. one outbound intro message from us
2. one inbound positive reply from the lead
```

Everything else goes to Human Review.

This is intentional because testing should be conservative for the next few days.

Later, after testing, the logic can be gradually expanded to handle older thread history by checking the newest inbound reply plus the closest prior outbound context. But that is **not the current rule**.

---

## 3. Current Strict Rule

A conversation is eligible for requirements-template preview only when:

```text
ordered.length === 2
AND ordered[0] is our intro template
AND ordered[1] is inbound from the lead
AND inbound reply is clearly positive
```

Positive signals currently include words like:

```text
yes, yeah, yep, interested, available, schedule, showing, tour, see,
today, tomorrow, Sunday, Monday, Tuesday, Wednesday, Thursday, Friday, Saturday
```

Negative or unsafe signals should block auto-selection and go to Human Review, including:

```text
stop, unsubscribe, wrong number, not interested, no longer interested,
already found, too expensive, scam, who is this
```

Human Review should receive:

```text
- threads with more than 2 messages
- threads missing phoneNumberId or participants
- replies that are not clearly positive
- wrong number / stop / not interested replies
- no matching eligible lead
- multiple matching eligible leads
- template render failure
- empty rendered template
- missing matched lead apartment address
- later: Web Auto send failures
- later: pipeline update failures
```

## 5. Current Trigger Model

The current handoff/build is **polling-based**, not webhook-based yet.

Current trigger:

```text
Run Now button
or frontend polling interval
→ POST /api/messages-automation/run-now
→ fetch recent Quo/OpenPhone conversations/messages
→ compare against message_automation_state.last_checked_at
→ process new messages
```

Current new-message detection is based on:

```text
message timestamp > message_automation_state.last_checked_at
```

The Rescan Latest button calls:

```text
POST /api/messages-automation/run-now?ignoreCheckpoint=1
```

That ignores `last_checked_at` for testing.

Clear Monitor now resets:

```text
last_checked_at = null
polling_enabled = false
status = idle
```

## 6. Future Trigger Model: Quo/OpenPhone Webhook

Later, add a real inbound webhook so Quo/OpenPhone notifies Mission Control when a new message arrives.

Future flow:

```text
Lead replies in Quo/OpenPhone
→ Quo sends message.received webhook
→ Mission Control webhook route receives payload
→ extract message id, phone, text, timestamp, conversation id
→ upsert into public.messages using external_message_id
→ pass message into same automation decision processor
→ render preview or create Human Review item
```

Recommended webhook route:

```text
mission-control-dashboard/app/api/messages-automation/webhook/route.ts
```

Alternative route:

```text
mission-control-dashboard/app/api/quo/webhooks/messages/route.ts
```

Preferred route:

```text
app/api/messages-automation/webhook/route.ts
```

because the webhook belongs to the automation system.

### Webhook newness should not use last_checked_at

Polling can use `last_checked_at`, but webhook processing should use:

```text
external_message_id
```

Production-safe newness logic:

```text
If external_message_id already exists in public.messages or ai_decisions:
    skip duplicate
Else:
    treat as new inbound event
```

### Webhook should not auto-send at first

First webhook version should only:

```text
receive → log → match → render preview → Human Review if unsafe
```

Do not enable automatic SMS send until webhook payloads and dedupe are proven.

## 19. Current Known Risks

### Risk 1 — Template renderer depends on address matching

If `apt_address` in `dashboard_leads` does not match what QuoSender expects, template variables may be missing or wrong.

Mitigation:

```text
Show raw QuoSender render response in preview pane.
```

### Risk 2 — Timestamp checkpoint can hide messages during testing

If `last_checked_at` is newer than the message timestamp, polling will skip it.

Mitigation:

```text
Use Rescan Latest
or Clear Monitor to reset last_checked_at = null
```

### Risk 3 — Polling only runs while dashboard is open

Current frontend polling is not true background automation.

Mitigation later:

```text
Use n8n cron
or server cron
or webhook
```

### Risk 4 — Same phone can have multiple apartment inquiries

Current safe lookup must return exactly one eligible lead.

Mitigation:

```text
matched_count = 0 → Human Review
matched_count = 1 → continue
matched_count > 1 → Human Review
```

### Risk 5 — pipeline_status currently stale

Many intro-sent leads still have:

```text
pipeline_status = new_lead
```

Mitigation:

```text
Use current_status + conversation_stage for current matching.
Later fix n8n/mark_intro_sent to set pipeline_status = contacted.
```
