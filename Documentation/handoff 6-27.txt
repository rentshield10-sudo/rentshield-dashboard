# Mission Control Messages Automation — Handoff

**Date:** 2026-06-26  
**Scope:** Mission Control Messages tab + Quo/OpenPhone webhook automation + AnyClick autosend wiring  
**Current mode:** Webhook-driven automation. Eligible replies auto-send the requirements template through AnyClick. Non-eligible replies go to Human Review.

---

## 1. Current Goal

The Messages automation is being built to handle inbound Quo/OpenPhone replies.

The current rule is:

```text
Inbound webhook reply
→ If it qualifies under the strict one-reply rule, auto-send the requirements template
→ Otherwise send it to Human Review
```

The system is no longer meant to show an “Add Template Reply to Queue” button for this first automation path. The Messages tab should display what happened, including the visible job queue window, but the actual decision happens in the webhook route.

---

## 2. Strict Current Automation Rule

For now, the automation should only send the requirements template when all of these are true:

```text
1. The webhook event is inbound / message.received.
2. The event came from the Primary Quo/OpenPhone inbox.
3. The message is not a duplicate webhook message.
4. The inbound reply is positive or engaged.
5. Exactly one eligible dashboard lead is matched.
6. The matched lead has an apartment address.
7. The requirements template renders successfully.
8. AnyClick send succeeds.
9. The lead pipeline update succeeds.
```

Anything else goes to Human Review.

The practical meaning of the “1 reply rule” right now is:

```text
Only leads currently eligible for auto-reply are allowed to send:
current_status = contacted
conversation_stage = intro_sent
```

This is enforced through the Supabase RPC:

```sql
find_single_contacted_lead_for_auto_reply(p_phone text)
```

The current code does not use `pipeline_status = contacted` for eligibility, because real rows often still have:

```text
pipeline_status = new_lead
```

while the actual useful eligibility fields are:

```text
current_status = contacted
conversation_stage = intro_sent
```

## 11. Important Testing Notes

### Polling should stay paused during webhook autosend testing

If polling is running while webhooks are also active, the same lead/message can appear twice:

```text
1. Webhook processes the inbound message.
2. Polling later scans the conversation and processes the same conversation/message.
```

For now:

```text
Use webhook for real automation.
Keep polling paused.
Use Run Now only for manual testing.
```

### Duplicate webhook protection

Webhook duplicate protection is based on:

```text
public.messages.external_message_id
```

If Quo/OpenPhone sends the exact same webhook message twice, the second one should log duplicate and not send.

### Cross-conversation duplicate risk

If Quo/OpenPhone creates a new `messageId` for the same human text, the current dedupe may not catch it. Later, the backend queue should add stronger dedupe such as:

```text
phone + inboundText + templateKey + time window
```

or a dedicated queue table with unique constraints.

## 14. Suggested Future Improvement

After tomorrow’s Human Review UI, add a true backend queue table.

Suggested table:

```sql
create table if not exists public.message_send_jobs (
  id bigserial primary key,
  created_at timestamptz default now(),
  updated_at timestamptz default now(),
  status text not null default 'pending',
  phone text not null,
  lead_id text,
  template_key text,
  inbound_text text,
  outbound_text text not null,
  external_message_id text,
  external_conversation_id text,
  source text default 'messages_automation',
  attempts int default 0,
  last_error text,
  anyclick_payload jsonb,
  anyclick_result jsonb,
  ai_decision_id bigint
);
```

Add uniqueness/dedupe later:

```sql
unique(phone, template_key, external_message_id)
```

Then webhook should enqueue jobs instead of directly calling AnyClick. A worker route should process one job at a time:

```text
/api/messages-automation/process-next-job
```

That will prevent multiple simultaneous AnyClick jobs.
