# RentShield / Mission Control Pipeline + Booking Update Handoff

_Last updated from the current implementation session._

## 1. High-Level Goal

We implemented a simple lead pipeline/tagging system inside the Mission Control dashboard.

The goal is:

1. Zillow lead scraper collects rental leads.
2. Leads land in Google Sheets and/or Supabase.
3. n8n processes new rows and triggers outbound automation.
4. Mission Control dashboard displays lead status, bookings, and follow-up pools.
5. Booking tab can add showing appointments.
6. When a booking is created or updated, the matching lead pipeline status should update in Supabase.
7. Leads tab reads Supabase and shows the updated pipeline state.

The important design decision: this is a **simple pipeline status system**, not a complex job/event/audit system.



## 3. Pipeline Statuses Implemented

The current simple pipeline statuses are:

```text
new_lead
contacted
requirements_sent
schedule_sent
booked
confirmed
showed
no_show
reschedule_needed
cancelled
nurture
lost
```

### Meaning

| Status | Meaning |
|---|---|
| `new_lead` | Lead exists but no intro/outbound action yet. |
| `contacted` | Intro SMS/contact message sent. |
| `requirements_sent` | Requirements/request info message sent. |
| `schedule_sent` | Schedule/showing availability sent. |
| `booked` | Showing appointment created. |
| `confirmed` | Appointment confirmed. |
| `showed` | Lead attended the showing. |
| `no_show` | Lead booked/confirmed but did not attend. |
| `reschedule_needed` | Lead needs another showing time. |
| `cancelled` | Appointment cancelled and not clearly rescheduling. |
| `nurture` | Lead should be followed up later. |
| `lost` | Dead lead, wrong number, duplicate, not interested, stop, or unqualified. |

### Happy Path Shown in Top Progress Bar

The Leads tab top pipeline progress line shows only the main happy path:

```text
New Lead → Contacted → Requirements Sent → Schedule Sent → Booked → Confirmed → Showed
```

Side statuses are not part of the straight progress line:

```text
No Show
Reschedule Needed
Cancelled
Nurture
Lost
```

Those should display as the current/special status when selected.

```sql
alter table public.dashboard_leads
add constraint dashboard_leads_pipeline_status_check
check (
  pipeline_status in (
    'new_lead',
    'contacted',
    'requirements_sent',
    'schedule_sent',
    'booked',
    'confirmed',
    'showed',
    'no_show',
    'reschedule_needed',
    'cancelled',
    'nurture',
    'lost'
  )
);
```

### C. Updated `dashboard_leads_clean` view

Important note:

Postgres does not allow inserting a new view column in the middle of an existing view using `create or replace view` if it changes the order/name mapping. So `pipeline_status` was added at the end of the view.

SQL pattern:

```sql
create or replace view public.dashboard_leads_clean as
select
  lead_id,
  created_at,
  lead_name,
  phone,
  apt_address,
  source,
  current_status,
  conversation_stage,
  last_inbound_sms,
  last_inbound_at,
  last_outbound_sms,
  last_outbound_at,
  selected_slot,
  needs_human_review,
  stop_automation,
  notes,
  case
    when created_at is null or trim(both from created_at) = '' then null::timestamp with time zone
    else created_at::timestamp with time zone
  end as created_at_ts,
  case
    when last_inbound_at is null or trim(both from last_inbound_at) = '' then null::timestamp with time zone
    else last_inbound_at::timestamp with time zone
  end as last_inbound_at_ts,
  case
    when last_outbound_at is null or trim(both from last_outbound_at) = '' then null::timestamp with time zone
    else last_outbound_at::timestamp with time zone
  end as last_outbound_at_ts,
  case
    when lower(coalesce(needs_human_review, '')) = any (array['true', 'yes', '1']) then true
    else false
  end as needs_human_review_bool,
  case
    when lower(coalesce(stop_automation, '')) = any (array['true', 'yes', '1']) then true
    else false
  end as stop_automation_bool,
  pipeline_status
from public.dashboard_leads;
```

### D. Verify `pipeline_status` from view

```sql
select

  lead_name,
  phone,
  apt_address,
  pipeline_status

limit 10;
```

## 5. RPC Function Added

Browser/client-side `.update()` to `dashboard_leads` was not reliably updating `pipeline_status` from the Booking tab. The booking insert into `dashboard_showing_appointments` worked, but `dashboard_leads.pipeline_status` stayed `new_lead`.

To fix this, we added a Supabase RPC function with `security definer`.

### Function: `public.update_dashboard_lead_booked`

Purpose:

- Called by Booking tab after inserting a booking.
- Updates the matching `dashboard_leads` row.
- Sets pipeline to `booked`.

SQL:

```sql
create or replace function public.update_dashboard_lead_booked(
  p_lead_id text,
  p_showing_at text
)
returns table (
  updated_lead_id text,
  updated_pipeline_status text
)
language plpgsql
security definer
set search_path = public
as $$
begin
  return query
  update public.dashboard_leads dl
  set
    pipeline_stage = 'showing_scheduled',
    pipeline_status = 'booked',
    appointment_status = 'booked',
    confirmation_status = 'pending_confirmation',
    attendance_status = 'pending',
    showing_at = p_showing_at,
    last_pipeline_update_at = now()
  where dl.lead_id::text = p_lead_id
  returning
    dl.lead_id::text,
    dl.pipeline_status::text;
end;
$$;

grant execute on function public.update_dashboard_lead_booked(text, text) to anon;
grant execute on function public.update_dashboard_lead_booked(text, text) to authenticated;
```

### Test RPC directly

```sql
select *
from public.update_dashboard_lead_booked(
  '463',
  '2026-06-12 22:00:00+00'
);
```

### Verify lead update

```sql
select
  lead_id,
  lead_name,
  phone,
  apt_address,
  pipeline_status,
  pipeline_stage,
  appointment_status,
  confirmation_status,
  attendance_status,
  showing_at,
  last_pipeline_update_at
from public.dashboard_leads
where lead_id = '463';
```

Expected result:

```text

pipeline_stage = showing_scheduled
appointment_status = booked
confirmation_status = pending_confirmation
attendance_status = pending
```

### Booking-to-Pipeline Mapping

Current booking status mapping:

```text
Add booking              → pipeline_status = booked
confirmation confirmed  → pipeline_status = confirmed
attendance attended     → pipeline_status = showed
attendance no_show      → pipeline_status = no_show
attendance cancelled    → pipeline_status = cancelled
attendance rescheduled  → pipeline_status = reschedule_needed
delete booking          → pipeline_status = reschedule_needed
```

### Helper Function Added in BookingTab

```ts
function getPipelineStatusFromBooking({
    appointmentStatus,
    confirmationStatus,
    attendanceStatus,
}: {
    appointmentStatus?: string | null;
    confirmationStatus?: string | null;
    attendanceStatus?: string | null;
}) {
    const appointment = String(appointmentStatus || "").toLowerCase();
    const confirmation = String(confirmationStatus || "").toLowerCase();
    const attendance = String(attendanceStatus || "").toLowerCase();

    if (attendance === "attended") return "showed";
    if (attendance === "no_show") return "no_show";
    if (attendance === "cancelled") return "cancelled";
    if (attendance === "rescheduled") return "reschedule_needed";

    if (confirmation === "confirmed") return "confirmed";

    if (appointment === "completed") return "showed";
    if (appointment === "confirmed") return "confirmed";
    if (appointment === "booked") return "booked";
    if (appointment === "no_show") return "no_show";
    if (appointment === "cancelled") return "cancelled";
    if (appointment === "rescheduled") return "reschedule_needed";

    return "booked";
}
```

## 8. Debugging History / Important Lessons

### Problem 1: View column order error

Error:

```text
cannot change name of view column "last_inbound_sms" to "pipeline_status"
```

Cause:

`pipeline_status` was inserted in the middle of an existing view definition.

Fix:

Add `pipeline_status` at the end of `dashboard_leads_clean`.

---

### Problem 2: Duplicate React keys

Error:

```text
Encountered two children with the same key
```

Cause:

Some `lead_id` values repeat or rows are not unique enough for React rendering.

Fix:

Use a row key based on:

```text
lead_id
phone
apt_address
created_at/created_at_ts
visible index
```

---

### Problem 3: Booking added but Leads tab stayed New Lead

Observed:

```text
dashboard_showing_appointments.appointment_status = booked
dashboard_leads.pipeline_status = new_lead
```

Cause:

Booking insert was working, but `dashboard_leads` update was not.

Fix:

Added RPC:

```text
public.update_dashboard_lead_booked
```

Then Booking tab calls RPC after inserting the appointment.

---

### Problem 4: Duplicate leads / same person different apartments

Example:

Same person/phone can exist with multiple apartment rows.

So the system should be careful when matching by:

```text
lead_id only
```

The current Booking tab tries to find a matching dashboard lead row by:

```text
schedule apartment + phone match
```

then falls back to:

```text
foundLead.lead_id
```

This helps avoid updating the wrong apartment row.

### Backfill existing booked appointments into dashboard leads

Use when old appointments exist but leads still say `new_lead`:

```sql
update public.dashboard_leads dl
set
  pipeline_status = case
    when a.attendance_status = 'attended' then 'showed'
    when a.attendance_status = 'no_show' then 'no_show'
    when a.attendance_status = 'cancelled' then 'cancelled'
    when a.attendance_status = 'rescheduled' then 'reschedule_needed'
    when a.confirmation_status = 'confirmed' then 'confirmed'
    when a.appointment_status = 'confirmed' then 'confirmed'
    when a.appointment_status = 'completed' then 'showed'
    when a.appointment_status = 'cancelled' then 'cancelled'
    when a.appointment_status = 'rescheduled' then 'reschedule_needed'
    when a.appointment_status = 'no_show' then 'no_show'
    else 'booked'
  end,
  pipeline_stage = case
    when a.attendance_status = 'attended' then 'attended'
    when a.attendance_status = 'no_show' then 'no_show'
    when a.attendance_status = 'cancelled' then 'cancelled'
    when a.attendance_status = 'rescheduled' then 'rescheduled'
    when a.confirmation_status = 'confirmed' then 'confirmed'
    else 'showing_scheduled'
  end,
  appointment_status = a.appointment_status,
  confirmation_status = a.confirmation_status,
  attendance_status = a.attendance_status,
  showing_at = a.showing_at,
  last_pipeline_update_at = now()
from public.dashboard_showing_appointments a
where dl.lead_id::text = a.lead_id::text
  and a.appointment_status = 'booked';
```

## 13. One-Sentence Handoff Summary

We added a simple `pipeline_status` system to Mission Control so scraped Zillow leads can move through `new_lead → contacted → requirements_sent → schedule_sent → booked → confirmed → showed`, with Booking tab now updating Supabase through an RPC when appointments are created, and Leads tab showing searchable/filterable/selectable pipeline rows for follow-up and QuoSender workflows.
