### 2. Local Auto-Click / Quo Web Sender Server

**Purpose:** Send SMS through the Quo/OpenPhone web UI by browser automation/clicking, instead of sending directly through the paid API.

Why this exists:

- Quo/OpenPhone charges per SMS send through API usage.
- The local auto-click sender uses the web UI and clicks the same elements a user would click.
- This sender is already working.

Important behavior:

- This server should **not receive multiple direct webhook requests at the same time**.
- Messages must go through a queue first.
- The queue ensures messages are processed one at a time.

Known working auto-click result shape from `message_send_jobs.anyclick_result`:

```json
{
  "success": true,
  "flow_id": "flow_1776996361867_nxr811",
  "message": "Flow completed successfully",
  "current_url": "https://my.quo.com/inbox/PNAO2aXSml/c/...",
  "inputs_used": {
    "phone": "+19083576619",
    "message": "We are able to show the unit tomorrow Wednesday 6PM at 242 Hillcrest Ter, Roselle, NJ 07203, will you join?",
    "parameters": "+19083576619"
  },
  "steps_executed": 5
}
```

Known click steps include:

- Select primary inbox: `Primary(201) 350-1990`
- Click `Send a message`
- Fill participant input
- Fill message input
- Click send message

Important queue payload shape already seen:

```json
{
  "inputs": {
    "phone": "+19083576619",
    "message": "SMS text here",
    "parameters": "+19083576619"
  }
}
```

Important rule:

> The webhook/automation logic should insert into `public.message_send_jobs`. The worker/auto-click sender should claim and process queued jobs. The webhook should not directly call the auto-click sender for every inbound event.

```text

→ intro message is sent
→ lead replies in Quo/OpenPhone
→ webhook captures inbound SMS
→ Supabase stores message/decision state
→ automation decides what to do
→ eligible replies create queued SMS jobs
→ local auto-click sender sends queued SMS
→ Supabase updates lead pipeline
→ ambiguous/unsafe replies go to Human Review
```


If the reply is not clearly positive or safe:

## 3. Important Logic Correction

There is a suspected issue in the existing webhook logic.

The logic may currently be deciding what to reply based too much on:

```text
phone number + inbound message text
```

It should instead decide based on:

```text
normalized phone
+ exact matched lead
+ exact apartment/property
+ conversation_id / external_conversation_id when available
+ latest outbound message for that exact lead/property/conversation
+ latest outbound template_key / intent
+ pipeline_status
+ conversation_stage
+ stop_automation / human review flags
```

Important risk:

> If the same phone number has multiple apartment inquiries, choosing the last outbound by phone only can select the wrong context and send the wrong next message.

Safer rule:

```text
0 matching eligible leads → Human Review
1 matching eligible lead → continue automation
2+ matching eligible leads → Human Review
```

## 4. Booking Automation Rule for Tomorrow

The next feature is **not booking an appointment immediately**. The next feature is sending the next showing schedule after a positive requirements reply.

### Trigger

Only trigger this flow when:

```text
lead replies to the requirements SMS
```

The system should confirm this by checking one or more of:

- last outbound template was `02_requirements_request_v1`
- last outbound intent was requirements-related
- lead `pipeline_status = requirements_sent`
- lead `conversation_stage = requirements_sent` or equivalent

### Required Conditions

Before auto-sending the booking/showing schedule:

```text
- inbound message is from the lead, not outgoing/delivered event
- message was not already processed
- external_message_id is not duplicated
- exactly one safe lead/property match exists
- lead is not stopped from automation
- lead is not already in human review
- lead is not already booked/confirmed/showed/lost/cancelled
- last outbound context is requirements SMS
- inbound reply is clearly positive / qualified enough
- a future available schedule exists in the Booking tab table
```

### If Positive

```text
find next future schedule
→ compose showing invitation message
→ insert pending job in message_send_jobs
→ update lead pipeline to schedule_sent
```

### If Not Positive / Ambiguous

```text
send nothing automatically
→ create/update Human Review item
→ mark lead/message as needing human review
```

## 6. Booking Schedule Selection Rule

The normal schedule pattern is:

```text
Monday, Wednesday, Friday, Saturday
```

But this must **not** be hardcoded.

Reason:

- The Booking tab is manually edited.
- Sometimes the schedule changes.
- Automation should respect whatever is currently saved in the Booking tab.

Recommended schedule lookup:

```text
Find the next available dashboard_showing_schedules row
for the lead's apt_address
where showing_at is in the future
and schedule_status is not cancelled/full
and open slots remain
```

Also discussed rule:

> If today is already the showing schedule date, a new lead who replies today should receive the **next** schedule date, not today's same-day schedule.

Safer version:

```text
showing_at date must be greater than today's date in America/New_York
```

This avoids inviting new leads into a same-day showing after the day has already started.

## 7. Message Queue Rule

The auto-reply system should never blast the local sender with direct simultaneous requests.

Correct design:

```text
Webhook / decision logic
→ insert pending row into public.message_send_jobs
→ return quickly

Queue worker / local sender
→ claim one pending job
→ call local auto-click Node server
→ update job status
→ insert outbound message record
→ update lead pipeline/last outbound fields
```

This preserves queue behavior and prevents the local browser sender from receiving multiple concurrent requests.

### Next Schedule Lookup Concept

```sql
select
  s.id as schedule_id,
  s.apt_address,
  s.showing_at,
  to_char(s.showing_at at time zone 'America/New_York', 'FMDay FMHH12:MI AM') as sms_schedule_label,
  s.schedule_status,
  s.max_slots,
  count(a.id) filter (
    where coalesce(a.appointment_status, '') not in ('cancelled', 'canceled')
  ) as active_bookings,
  coalesce(s.max_slots, 100) - count(a.id) filter (
    where coalesce(a.appointment_status, '') not in ('cancelled', 'canceled')
  ) as open_slots
from public.dashboard_showing_schedules s
left join public.dashboard_showing_appointments a
  on a.schedule_id = s.id
where lower(trim(s.apt_address)) = lower(trim(:apt_address))
  and (s.showing_at at time zone 'America/New_York')::date
      > (now() at time zone 'America/New_York')::date
  and coalesce(s.schedule_status, 'available') not in ('cancelled', 'canceled', 'full')
group by
  s.id,
  s.apt_address,
  s.showing_at,
  s.schedule_status,
  s.max_slots
having count(a.id) filter (
  where coalesce(a.appointment_status, '') not in ('cancelled', 'canceled')
) < coalesce(s.max_slots, 100)
order by s.showing_at asc
limit 1;
```
